# Planning and task management in Pi and Waku

Reviewed 2026-10-08. Remote HEADs were checked with `git ls-remote`: Pi `6fb2e7815167e6b19006fc526d1a5d0f5f998787`, Waku `763d3e79f34a2deca805e815b3b230188579e16b`. Findings below come from official source at those revisions. This is a source review; no model runs, crash experiments or comparative benchmarks were performed. Proposed Lina behavior is identified separately from observed implementation.

## What these agents actually provide

| Surface | Who decides | Stored representation | What it does not establish |
| --- | --- | --- | --- |
| Pi core loop | Model chooses the next tool; host hooks may continue/end a turn | Conversation and tool-result history | A built-in plan scheduler or mandatory task ledger |
| Pi optional `plan-mode` example | User enters planning mode and chooses execution/refinement; model proposes steps and marks completion | Custom session entries and numbered `{step,text,completed}` items | Evidence-verified completion, dependencies or durable task execution |
| Pi optional `todo` example | Model invokes `todo`; user can inspect | Branch-reconstructed tool-result snapshots of `{id,text,done}` | Dispatching work or automatically continuing until every item is done |
| Pi durable plan example | Host configures planning access; model calls `submit_plan` | Transactionally updated, conversation-scoped document | A dependency scheduler, per-step verification or production default CLI feature |
| Waku ordinary loop | Model chooses tools until it replies; iteration limit constrains it | Working messages plus persisted chat/telemetry | A structured built-in plan/task ledger in the checked paths |
| Waku graph workflows | Authored topology and code routers control execution; models provide bounded outputs | In-memory graph state, path and trace | A dynamically generated model plan or resumable checkpoint engine |

Pi explicitly describes plan mode as an extension/package choice rather than a default feature. Its core loop advances through model/tool turns, accepts steering and host preparation hooks, and can end on a host decision. Planning text may occur in model responses, but that alone is not an explicit task model. [Pi orientation](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/README.md#L13-L21), [Core loop](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/agent/src/agent-loop.ts#L160-L310).

## Pi plan mode: optional exploration and progress tracking

The example enables planning via `/plan`, a shortcut or `--plan`. It removes the built-in `edit` and `write` tools, preserves other active tools, adds exploration tools, and blocks non-allowlisted `bash` commands through the tool-call hook. It then injects planning instructions before the agent starts. This is an actual availability/filter mechanism for named built-ins; it is **not a general side-effect sandbox**: custom active tools are preserved and the shell filter uses text patterns rather than a shell parser or environment policy. Pi's repository separately states it has no built-in process/filesystem/network permission system. Lina should put restrictions in Tools/Safety/environment controls, independently of planning instructions. [Availability and tool interception](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/examples/extensions/plan-mode/index.ts#L21-L174), [Shell filtering](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/examples/extensions/plan-mode/utils.ts#L6-L101), [Permissions boundary](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/README.md#L88-L96).

The extension parses numbered items following a `Plan:` heading from the last assistant message. This is a presentation parser, not a registered structured planning tool. It cleans and truncates item text to 50 characters, so it should not be adopted as Lina's full-fidelity technical plan record. The interactive UI offers execution, staying in planning mode and refinement; headless execution does not receive that UI approval flow. [Plan extraction](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/examples/extensions/plan-mode/utils.ts#L103-L149), [Interactive decision](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/examples/extensions/plan-mode/index.ts#L279-L337).

Execution restores the prior tool set and queues the plan and execution instruction as follow-ups. Before each agent start, remaining steps are reinjected. At turn end, assistant text containing `[DONE:n]` marks that step complete; at agent end, all completed items cause a completion message and clearing of execution state. **The completion signal is the model's assertion.** There is no check in these handlers that a test passed, an artifact exists, a subagent result was accepted, or a requested external action actually succeeded. An assistant can also finish a run with incomplete items; the extension retains the execution state but does not itself run an unlimited continuation scheduler. [Context injection and progress](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/examples/extensions/plan-mode/index.ts#L200-L277), [Execution follow-up](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/examples/extensions/plan-mode/index.ts#L307-L329).

State is appended in custom `plan-mode` entries. Resume reads the latest such entry and rescans assistant completion markers after the last execution marker. Ordinary custom entries do not enter model context; injected custom messages do. The saved state remains inspectable even when older model-visible context is compacted. However, this implementation restores from `getEntries()` rather than the active branch and registers `session_start`, not a `session_tree` reconstruction handler. It therefore should not be described as having the same branch-specific task restoration semantics as the separate todo example. This is a source observation, not a tested branching defect. [Plan persistence and resume](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/examples/extensions/plan-mode/index.ts#L116-L123), [Resume reconstruction](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/examples/extensions/plan-mode/index.ts#L339-L389), [Context and branch APIs](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/src/core/session-manager.ts#L437-L510), [Session accessors](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/src/core/session-manager.ts#L1469-L1522).

## Pi todo tool: structured state without a scheduler

The official example registers `todo` with `action: list | add | toggle | clear`, optional `text` and optional numeric `id`. Items have a boolean `done`; there is no `in_progress`, `blocked`, dependency, owner, evidence or execution-attempt field. Missing text/ID and unknown IDs return error details. This deliberately small tool is useful evidence for exposing task updates through normal tool dispatch; it is not evidence of a full planning engine. [Types and schema](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/examples/extensions/todo.ts#L19-L37), [Operations](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/examples/extensions/todo.ts#L135-L219).

Each result carries the current list and next ID in result details. Session start and tree changes reconstruct state by reading `todo` results along the active branch. Consequently, task state is recoverable independently of whether the latest list remains in the model's compacted context; the model can call `list` again. There is no automatic todo-context reinjection or compaction handler in this example. `toggle` reverses state, so blindly replaying the same logical update is not idempotent; `clear` also resets the ID counter. Lina should use stable IDs and explicit target statuses if updates can be retried or correlated across runs. [Branch reconstruction](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/examples/extensions/todo.ts#L104-L140), [Toggle and clear](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/examples/extensions/todo.ts#L172-L205).

## Pi durable plan document: stronger storage, deliberately small behavior

The separate `pi-durable` example defines `app.plan` version 1 with `steps: string[]`, conversation scope, rewindable history and `fork: asOf`. Its `submit_plan` schema accepts a string array, updates the document inside a transaction, and returns termination control. The host selects only `read` and `submit_plan` while planning; leaving planning restores default extensions/tools. These are concrete document ownership and capability-selection mechanisms, not only prompt requests. The example itself uses `MemoryStorage` and a faux provider; it does not demonstrate disk crash recovery for that plan. [Complete plan example](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/test/examples/27-plan-mode.ts#L26-L111).

The package documents committed tool intent, opt-in safe replay, interrupted results for unsafe replay, persisted pending work, and compaction preserving stored entries. Those are general durable-runtime facilities. They do not turn the plan example into step dispatch, completion verification or subagent assignment: its document contains only steps, and implementation after leaving plan mode is a subsequent input. Lina can reuse State's recovery guarantees while keeping Planning's logical statuses separate from execution-task status. [Durable tools and replay](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/README.md#L151-L168), [Pending work](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/README.md#L109-L115), [Compaction](https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/durable/README.md#L336-L350).

## Waku: implicit planning and authored graph workflows

In the checked default registry, loop, SQLite schema and experimental tool definitions, there is no built-in `plan`, `todo` or task-progress tool/table. The core registry provides domain tools, memory management and optional integrations; experimental `delegate_task` delegates coding to Pi. External MCP servers may expose other tools, so this finding is limited to Waku's checked built-ins, not every configured deployment. [Registry](https://github.com/ShenSeanChen/waku-agent/blob/763d3e79f34a2deca805e815b3b230188579e16b/waku/tools/__init__.py#L14-L83), [Stored schema](https://github.com/ShenSeanChen/waku-agent/blob/763d3e79f34a2deca805e815b3b230188579e16b/waku/db.py#L12-L80), [Delegation](https://github.com/ShenSeanChen/waku-agent/blob/763d3e79f34a2deca805e815b3b230188579e16b/waku/tools/experimental.py#L186-L317).

The ordinary loop executes requested tools serially, appends their results and asks the model again. A reply with no tools ends the turn. Reaching `max_iterations` causes one final tools-disabled response that should explain missing/failed work; this is an execution limit, not successful completion of a plan. The app uses a bounded history window, persists completed exchanges and telemetry, and trims previously read large results between calls. None of those checked mechanisms reinjects a structured active plan. [Loop exit and execution](https://github.com/ShenSeanChen/waku-agent/blob/763d3e79f34a2deca805e815b3b230188579e16b/waku/loop/agent.py#L117-L209), [History and trimming](https://github.com/ShenSeanChen/waku-agent/blob/763d3e79f34a2deca805e815b3b230188579e16b/waku/app.py#L207-L244), [Completed exchange persistence](https://github.com/ShenSeanChen/waku-agent/blob/763d3e79f34a2deca805e815b3b230188579e16b/waku/app.py#L128-L178).

Waku makes an explicit distinction between **skills**, instructions the model reads, and **graph workflows**, structure the engine executes. Skill matching uses keyword overlap and loads selected bodies; it does not create a dependency schedule or task ledger. This distinction is useful for Lina: a skill can recommend a plan, while a planning record stores actual progress and an execution scheduler runs admitted work. [Terminology](https://github.com/ShenSeanChen/waku-agent/blob/763d3e79f34a2deca805e815b3b230188579e16b/waku/graph/workflows/__init__.py#L1-L6), [Skill loader](https://github.com/ShenSeanChen/waku-agent/blob/763d3e79f34a2deca805e815b3b230188579e16b/waku/memory/procedural/loader.py#L47-L93).

The graph engine executes ready nodes in parallel waves, merges disjoint writes deterministically, waits for static dependencies, and uses code routers for conditional edges. Per-node visit limits and a global step limit constrain cycles; node exceptions are recorded and may take error routes. Its run-local readiness, visits and path live in memory: the checked engine has no checkpoint save/load or cooperative cancellation interface. Trace/history retention must not be presented as interrupted graph resumption. [Graph model](https://github.com/ShenSeanChen/waku-agent/blob/763d3e79f34a2deca805e815b3b230188579e16b/waku/graph/engine.py#L55-L109), [Runtime state, waves and errors](https://github.com/ShenSeanChen/waku-agent/blob/763d3e79f34a2deca805e815b3b230188579e16b/waku/graph/engine.py#L117-L214).

The shipped triage graph runs classification and calendar reading in parallel, then routes to a quick response or the existing agent loop. The gather graph runs four independent scans before synthesis and a code-based proposal/quiet decision; it withholds action tools from the synthesis model and writes a proposed digest for human review. These are actual workflow architectures, but their topology is authored in code, not generated by the model for each user goal. [Triage graph](https://github.com/ShenSeanChen/waku-agent/blob/763d3e79f34a2deca805e815b3b230188579e16b/waku/graph/workflows/triage.py#L89-L118), [Gather topology](https://github.com/ShenSeanChen/waku-agent/blob/763d3e79f34a2deca805e815b3b230188579e16b/waku/graph/workflows/gather.py#L111-L145), [Gather capability boundary](https://github.com/ShenSeanChen/waku-agent/blob/763d3e79f34a2deca805e815b3b230188579e16b/waku/graph/workflows/gather.py#L23-L36).

## Implications for Lina — proposal, not upstream claims

1. Keep planning optional. A direct model/tool loop is a legitimate path, not an incomplete planner.
2. Use a structured, full-fidelity plan record with stable step IDs. Rendering numbered text should be a projection; it should not be the canonical parser-dependent record.
3. Separate the model's proposed status from accepted completion evidence. An accepted tool/subagent result can support a step, but successful execution alone may not satisfy its acceptance criteria.
4. Persist plan revisions through State and inject a bounded current-plan projection through Context. Compaction should not make an unfinished task disappear, and child context should receive only its assigned scope.
5. Expose plan updates through registered Tools, with explicit target states and deduplication/revision checks. Avoid replay-sensitive toggles and reconstructing ownership from prose markers.
6. Keep Planning, Safety and scheduling distinct. Plan approval is not permission for every side effect. Selecting read-only capabilities should be enforced at the execution boundary, including custom tools/connectors.
7. Support authored workflows as an alternative to model-led replanning. Waku supplies a concrete reason: known independent steps can run without repeated planning calls. Preserve topology/strategy in experiment records.
8. Do not treat cancellation, an iteration limit, a paused approval or an interrupted child as completed work. Retain evidence and unresolved state for resume or revision.

These sources establish mechanisms and limitations. They do not establish which planning strategy improves Lina's task success, latency or cost; those require controlled comparisons with the same model, tools, scenarios and budgets.
