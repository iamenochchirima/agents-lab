# Jev Ultrafast posts: relevance to Anesu browser research

Checked 2026-09-25. The three [X posts](https://x.com/gregpr07/status/2100411066966749359), [follow-up link](https://x.com/gregpr07/status/2100411068426469552), and [diagram post](https://x.com/gregpr07/status/2100411547290046717) returned 403 when opened directly. A public syndication endpoint returned their text and the diagram image: the first reports a Jev browser-agent flight search in 7 seconds for $0.0039; the second links the [Jev Ultrafast repository](https://github.com/browser-use/jev-ultrafast); the third says "How it works in a nutshell" and shows operation and target fan-out. The primary repository below is the basis for the technical findings; the syndication endpoint is not independent evidence for the performance claims.

## Verified in primary sources

The [author's README](https://github.com/browser-use/jev-ultrafast/blob/main/README.md) describes a fresh indexed DOM action table on each observation. In [model.py](https://github.com/browser-use/jev-ultrafast/blob/main/jev_ultrafast/model.py), one TypeSafe request asks for an operation and compatible target choices in parallel; code uses only the target for the chosen operation. A separate small LLM generates field text when `TYPE_TEXT` is chosen. The default loop uses structured page state rather than screenshots. The README says `DONE` needs independent outcome verification and lists unsupported controls, including frames, shadow roots, uploads, and arbitrary keyboard widgets.

The [performance report](https://github.com/browser-use/jev-ultrafast/blob/main/docs/performance.md) records one verified Google Flights run at 7.073 seconds. Its timer excludes browser setup, initial navigation, and independent post-run verification. In three matched pairs on one task and Chrome profile, both versions passed 3/3; medians were 9.450 versus 7.092 seconds. The report calls this too small for a broad benchmark. It records $0.00006272 for two text-helper calls but no billed TypeSafe dollar amount, and excludes browser costs. Thus the post's **$0.0039 total-cost claim is unverified by the published measurements**.

Current [TypeSafe Choice docs](https://docs.typesafe.ai/primitives/choice) support fixed options, probabilities, confidence, and up to 255 options per Choice. [Speculative fan-out](https://docs.typesafe.ai/patterns/fan-out) supports several questions in one call, with code ignoring irrelevant answers. [State docs](https://docs.typesafe.ai/concepts/state) say Jev accepts text or structured JSON, not images. TypeSafe's [Jev 1.13 limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13) warn about large irrelevant state, indirection, numerical precision, adversarial content, and text generation. Its [line-by-line search recipe](https://docs.typesafe.ai/cookbooks/semantic_find) also shows how Jev can rank source IDs, but requires a separate answer-existence check and source reading.

## Inference for Anesu

This is useful as a **comparison design**, not evidence that Anesu should switch browser drivers or that Jev improves general web research. Anesu's [current browser contract](../../anesu/src/browser/README.md) gives the conversation model direct Cua browser tools. Its high-level computer runner has a Jev browser-candidate path, but the default instructions route ordinary browser chat through the typed tools and reserve that high-level tool for native work. A fair experiment could hold Cua observations, task goals, approvals, and outcome checks fixed while comparing direct model tool choice with a Jev operation/target policy. Research tasks should measure source coverage, correct citations, abstention on missing evidence, latency, cost, and recovery from changing pages. The flight demo establishes none of those research-quality outcomes. Exact-value extraction, comparison, and final synthesis would still need code checks or a generative model, consistent with TypeSafe's documented limits.
